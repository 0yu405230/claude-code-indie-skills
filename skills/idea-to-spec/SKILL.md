# idea-to-spec — アイデア→MVP仕様書変換

> 個人開発収益化Skill集(非公式・Claude Code対応)収録 / v0.1.0
> パイプライン位置: **[仕様化]** → 実装(nextjs-supabase-scaffold)→ 監査(project-audit)→ 販売文(jp-copywriting)→ ローンチ確認(launch-checklist)

個人開発者1人・週15〜25時間で、1〜2週間以内に公開できる規模のMVP仕様書を作る。機能を増やす方向ではなく**削る方向**に働くのが本Skillの本質。

## 発動すべき場面
- 「〜というサービス/アプリ/商品を作りたい」と言われたとき
- 機能の箇条書きメモを渡され「作って」と言われたとき(実装前に必ず仕様化)
- 仕様が固まっていないままコードを書き始めようとしているとき(いったん止めて発動)
- 既存プロジェクトへの大きめの機能追加を計画するとき(追加分をミニ仕様化)

**運用ルール:** 仕様書なしで実装・コード生成を始めない。実装依頼が先に来た場合も、まず本Skillで仕様化してから着手する。

## 使ってはいけない場面
- チーム開発・受託の正式な要件定義書が必要なとき(本Skillは個人MVP専用)
- 法規制・税務・医療の可否判断そのもの(リスクの「指摘」までに留め、判断は専門家・公式情報へ誘導)
- 完成済み仕様書の単純レビュー(指摘のみ行い、書き直しは指示があってから)

## 実行手順
1. 入力テンプレートの項目が埋まっているか確認。欠けた項目は**質問せずにまず仮置き**し、仕様書末尾「未確定事項」に必ず列挙する(質問するなら1回・3項目まで)
2. ターゲットの「痛み」を1文で定義する。痛みが書けないアイデアはその旨を正直に指摘する
3. ユーザーストーリーを**5本以内**に絞る。6本目以降の候補は全て「やらないことリスト」へ移す
4. 画面一覧(5画面以内)とデータモデル概要(テーブル名+主要カラムのみ)を書く
5. 課金設計仮説(無料枠/価格帯)を1案書き、「仮説」と明記する
6. リスクフラグ5点を必ず確認する: 法規制(士業法・景表法)/著作権/個人情報の預かり/API従量コスト/プラットフォーム規約(スクレイピング等)。該当なしでも「確認済み・該当なし」と書く
7. Day1〜Day14の実装ロードマップを書く(Day10までにデプロイ、残りはバッファ)
8. 品質チェックリストで自己検査してから出力する

## 入力テンプレート
```
【アイデア概要】(1〜3文)
【ターゲット】(誰の、どんな場面の痛みか)
【課金イメージ】(あれば。なければ「未定」)
【使える時間】(週◯時間 / 目標公開日)
【技術スタック】(未定なら「おまかせ」)
【制約・NG事項】(扱いたくないデータ、避けたい領域など)
```

## 出力フォーマット
```
# MVP仕様書: {プロダクト名(仮)}
## 1. 概要(3行以内)
## 2. ターゲットと痛み(痛みを1文で)
## 3. ユーザーストーリー(最大5本、「◯◯として△△したい、なぜなら□□」形式)
## 4. やらないことリスト(最低3項目。v2候補/永久にやらない を区別)
## 5. 画面一覧(5画面以内、各1行)
## 6. データモデル概要(テーブル名と主要カラムのみ)
## 7. 課金設計仮説(無料枠/価格帯 ※仮説と明記)
## 8. リスクフラグ(法規制/著作権/個人情報/APIコスト/規約 の5点を必ず記載)
## 9. 実装ロードマップ(Day1〜14、Day10デプロイ)
## 10. 未確定事項(仮置きした前提を列挙)
```

## 品質チェックリスト
- [ ] ユーザーストーリーが5本以内
- [ ] やらないことリストが3項目以上
- [ ] リスクフラグ5点が全て記載(「該当なし」も明記)
- [ ] 収益の断定表現がない(「稼げる」「必ず売れる」禁止)
- [ ] Day14以内に収まっている。収まらない場合はスコープ削減案を提示した
- [ ] 仮置きした前提が「未確定事項」に全て書かれている

## 禁止事項
- 収益の断定・保証表現(「月◯万円狙えます」等)
- ユーザーが指定していない大規模機能(チーム機能・管理画面・ネイティブアプリ等)の勝手な追加
- リスクフラグの省略。個人情報を預かる設計になる場合は必ず代替案(ユーザーの手元で処理する方式等)を併記
- 「未確定事項」を書かずに仮定を事実のように出力すること

## 免責・注意書き
本仕様書は個人開発の計画補助であり、法務・税務・事業性の保証ではありません。法規制に関わる項目は該当分野の専門家・公式情報で確認してください。

## 悪い出力例(こうしない)
> 機能一覧: ①ユーザー登録 ②SNS連携 ③AI要約 ④チーム共有 ⑤管理画面 ⑥API公開 ⑦モバイルアプリ…(20項目)
> これら全てを実装しましょう!このサービスは必ず人気が出ます!

NG理由: スコープ無限/やらないことリストなし/リスク検討なし/断定表現。

## 良い出力例(抜粋)
> **3. ユーザーストーリー**
> 1. 読書好きの社会人として、読んだ本のメモを貼り付けると要点3行に整理してほしい。なぜなら読み返す時間がないから
>
> **4. やらないことリスト**
> - モバイルアプリ(v2候補)/ 他ユーザーとの共有(需要検証後)/ 書籍本文の全文取り込み(永久にやらない: 著作権リスク)
>
> **8. リスクフラグ**
> - 著作権: 書籍本文の長文転載を促さないUI文言にする(要対応)
> - APIコスト: 1回の整理≒数円想定。無料枠は月10回に制限(要実測)
> - 個人情報/法規制/規約: 確認済み・該当なし

## コールドスタートテスト
**サンプル入力:**
```
【アイデア概要】読書メモをAIで整理するWebアプリを作りたい
【ターゲット】本は読むがメモが散らかる社会人
【課金イメージ】未定
【使える時間】週20時間 / 2週間後に公開したい
【技術スタック】おまかせ
【制約・NG事項】特になし
```
**合格基準(8割品質の定義):**
- ユーザーストーリー5本以内・やらないことリスト3項目以上・リスクフラグ5点全記載
- 著作権(書籍本文の扱い)とAPIコストへの言及がある
- Day14以内のロードマップがあり、Day10前後にデプロイが置かれている
- 収益断定表現がゼロ/課金まわりの仮置きが「未確定事項」に明記されている
